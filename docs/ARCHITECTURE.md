# Architecture

Gita Verse is a static website on Vercel that talks directly to a Supabase project. There is no build step and no application server of our own: the browser calls Supabase (database API, Auth and edge functions), and the edge functions call the paid providers (Gemini, ElevenLabs, Razorpay, MSG91).

```
Browser (index.html + app.js)
  ├── Supabase Auth ........ email/password, Google, mobile OTP (SMS via send-sms → MSG91)
  ├── Supabase REST/RPC .... verses, stored translations, visit/event logging
  ├── Edge functions ....... ask-krishna (Gemini), tts-krishna (Gemini + ElevenLabs),
  │                          get-my-access, create-payment-link (Razorpay)
  ├── /api/geo (Vercel) .... visitor city for the dashboard
  └── Meta Pixel ........... ad measurement (see TRACKING.md)
Razorpay ──webhook──> razorpay-webhook ──> user_accounts (unlocks Annual Access)
```

### Screens

The app is a single page. `showScreen(id)` switches between `<section class="screen">` elements: `home`, `ask` (Ask Krishna chat), `explore`, `chapter`, `detail` (one verse), `topicScreen`, `authScreen` (sign-in) and `accountScreen`.

## Backend (Supabase project `bkwvuckznpaawmqrjjgk`, Mumbai)

### Edge functions (`supabase/functions/`)

JWT verification at the gateway is **off** for every function (see `supabase/config.toml`); each function checks the caller itself.

| Function | Caller and check | What it does |
| --- | --- | --- |
| `ask-krishna` | Signed-in user, or a signed-out visitor's one free question | Retrieves relevant verses (curated topics + `search_gita`), asks Gemini for a reply that cites only those verses, validates every citation. Without Annual Access it claims the account's one free question (`claim_free_question`), or for a signed-out visitor the one answer before sign-up (`claim_anon_question`: one per visitor id, at most 10 a day per network and 300 a day in total), and refunds it if no answer comes back. |
| `tts-krishna` | Signed-in user with Annual Access | `operation: "translate"` returns a translated meaning (stored translation first, Gemini otherwise). Otherwise narrates text with ElevenLabs (Sanskrit chant voice for verses, v3 voice for meanings). |
| `get-my-access` | Signed-in user | Plan, expiry, `access_active`, `free_question_available`. |
| `create-payment-link` | Signed-in user | Body `plan`: `"annual"` (₹499, default) or `"monthly"` (₹149). With `{mode:"popup"}`: creates a Razorpay order for that price (notes `checkout: "popup"`, `product: "gita_verse_annual"` or `"gita_verse_monthly"`, `user_id`) and returns `order_id`, the public `key_id` and `prefill` (the user's phone or email) for the on-site checkout. Otherwise: a payment link for that price (same `product` note) (expires in 1 hour) that returns to `/?payment=success`. Either way the Razorpay reference is stored in `payment_transactions.payment_link_id`. |
| `razorpay-webhook` | Razorpay (HMAC signature) | On `payment_link.paid`, or `order.paid` for an order marked `checkout: "popup"` with a known `product`, checks that the amount is that product's price (₹499 annual, also the old ₹999 and ₹1,000 for checkouts opened before a price change; ₹149 monthly; ₹399 for the retired 3-month plan, still honoured for checkouts opened before it was withdrawn; links without a product are annual) and unlocks 1 year, 1 month or 3 months (stacked on top of any remaining access; `apply_annual_payment` sets the length from the amount, and every plan keeps `plan_status = 'annual'`). Orders from other products on the same Razorpay account are ignored. Idempotent. Every verified event is logged to `payment_events`. Then sends the server-side Meta Purchase (`_shared/meta.ts`) if Meta hasn't accepted it yet. |
| `meta-purchase-retry` | pg_cron every 10 min (`x-worker-token` from vault `meta_retry_token`) | Retries server-side Meta Purchases not yet accepted (see OPERATIONS). |
| `admin-stats` | Pinned admin email **and** user id | Dashboard data from the `admin_stats` SQL function; excludes the owner's test accounts from funnel counts. |
| `translation-worker` | Token from Vault (`x-worker-token`) | Pre-translates verse text into every language in the background. |
| `send-sms` | Supabase Auth "Send SMS" hook (Standard Webhooks signature) | Delivers the OTP through MSG91's DLT template. Indian numbers only. |
| `raga-music`, `gemini-health`, `razorpay-health` | – | Retired stubs (404/410). |

Shared code lives in `supabase/functions/_shared/`: `server.ts` (plans and prices `PLANS`, Gemini model and URL, server-key lookup, `adminClient()`) and `languages.ts`.

### Database

| Table | Purpose | Who can read |
| --- | --- | --- |
| `gita_chapters`, `gita_verses`, `verse_topics` | The Gita text, meanings, topic tags | Anyone (see note below) |
| `user_accounts` | One row per user: plan, payment, access expiry, free question used, sign-up source | The user's own row; writes are server-only |
| `payment_transactions` | Razorpay links and payments | The user's own rows; writes are server-only |
| `anon_questions` | Signed-out visitors who used their free answer (visitor id, hashed network address, time) | Server only |
| `payment_events` | Every verified Razorpay webhook event, summarised (see OPERATIONS.md) | Server only |
| `translation_sources`, `text_translations` | Verse-text pieces (keyed by SHA-256 of the English) and their translations | Translations: signed-in users |
| `translation_leases` | Which languages the worker is currently translating | Server only |
| `site_visits`, `site_events` | First-party analytics (see TRACKING.md) | Server only (written through `log_visit` / `log_event`) |
| `site_sessions` | Visible time on site per page load (for the admin dashboard) | Server only (written through `log_session`) |
| `chat_threads`, `chat_messages` | Signed-in users' Ask Krishna conversations (`chat-history.js`), shown as dated cards in the chat | The user's own rows (read, insert, delete) |
| `website_locales` | Website UI translations generated by `website-language` (13 Indian languages are also shipped as `locales/*.json`) | Server only |
| `bookmarks`, `reading_progress`, `user_preferences` | From the earlier Expo app; unused by the website | The user's own rows |

**Access rule for verses:** the database lets anyone read verse text. The paywall on verse pages is enforced in the app (`hasLifetimeAccess()`), not by the database. This was a deliberate product decision; don't lock it down in the database without agreement.

SQL functions called from the site or functions: `get_daily_verse`, `search_gita`, `log_visit`, `log_event`, `set_my_attribution`, `claim_free_question` / `refund_free_question`, `claim_anon_question` / `refund_anon_question` (server only), `admin_stats` (server only), `next_translation_batch`, `claim_translation_languages`, `translation_missing`, `translation_worker_token_ok`.

A new auth user gets a `user_accounts` row automatically (trigger `on_auth_user_created_account`).

## Key flows

**Free questions → sign-up.** A signed-out visitor's first question is answered straight away, without an account (`ask-krishna` with their `visitor_id`; the hashed network address is kept in `anon_questions` only to cap abuse). Under the answer, "Continue free" offers one more free question with a free account. A further signed-out question is saved (`savePendingQuestion`) and the visitor goes to sign-up; after sign-in (`afterSignIn`) it is sent, `ask-krishna` claims the account's free question, and the answer appears. After that, the paywall.

**Sign-in methods.** Mobile OTP (first on the screen), email/password, Google. Inside Instagram/Facebook/Messenger/Threads, Google is blocked by Google itself, so the app offers mobile/email first and, on Android, an "Open in Chrome" hand-off that carries the visitor id, `fbclid` and UTM tags.

**Payment.** `startLifetimePurchase` loads Razorpay's checkout script and asks `create-payment-link` for a pop-up order → the Razorpay checkout opens over Gita Verse with the buyer's phone or email filled in → Razorpay calls `razorpay-webhook` (`order.paid`, unlocks access) and the checkout's success handler runs `confirmPaidAccess`, which polls `get-my-access` until access is active, then fires Meta `Purchase` once. If an in-app browser reloads the page on return from the UPI app, a `sessionStorage` flag (`gitaCheckoutPending`) makes the next load confirm instead. If the checkout script can't load within 6 s, the old flow is used: payment link → Razorpay page → `/?payment=success` → `handlePaymentReturn`.

**Meanings in other languages.** Each language's stored translations are loaded once (`loadStoredTranslations`); anything missing is translated through `tts-krishna` and saved if it is a known piece. `translation-worker` fills the table ahead of time.

**Narration.** Text is split at sentence ends into a short first clip (≤ 220 characters) and larger later clips, each generated while the previous one plays, so audio starts in about 2 seconds.
